# Analytics SDK & Dashboard — Design Spec

Date: 2026-10-16
Status: Draft for review

## 1. Goal

Build a small, working, end-to-end analytics system:

1. **Browser SDK** — reusable library that tracks page views and custom events.
2. **Server SDK** — lightweight helper that sends trusted business events from a server.
3. **Ingestion + storage** — HTTP API that validates and stores events, and query endpoints over them.
4. **Dashboard** — traffic, unique visitors, sessions, popular pages, event trends, with date-range filtering.
5. **Restaurant demo** — a small app that uses both SDKs to show page visits, user activity and an order being created, all visible in the dashboard.

Priorities (from the assignment): a working end-to-end system and sound engineering decisions over feature count or visual polish; meaningful tests; simple local setup; documented assumptions, decisions and limitations.

## 2. Technology decisions

| Concern | Choice | Why |
|---|---|---|
| Language | TypeScript everywhere | One language across SDKs, API, UI; types document the event contract |
| Backend + frontend | Next.js (App Router) | Single framework for API routes and React UI; easy to explain |
| Database | SQLite via `better-sqlite3` | Zero install, single file, plain SQL, synchronous and fast |
| Validation | Zod | Declarative schemas shared by API and tests |
| Charts | Recharts | Simple React charting |
| Tests | Vitest | Fast, TS-native, works for SDK (jsdom) and server code |
| Monorepo | npm workspaces | No extra tooling; `npm install` at root installs everything |
| SDK build | tsup | Produces ESM + CJS + types for packages |

Laravel/PHP was the preferred backend. We chose Next.js full-stack so one framework covers the whole system, and because the dev machine had Node but no PHP. The API contract is framework-agnostic, so the backend could be ported to Laravel without changing the SDKs.

## 5. Identity model

- **anonymous_id** — random id (`anon_<uuid>`) generated on first visit; stored in `localStorage` with a first-party cookie fallback. Basis for **unique visitors**.
- **session_id** — `sess_<uuid>`; rotated after 30 minutes of inactivity (last-activity timestamp in `localStorage`). Basis for **sessions**.
- **user_id** — set by `identify(userId, traits?)` after the demo's fake login. Sends an `identify` event linking `anonymous_id` → `user_id`. Subsequent events carry both. Cleared by `reset()` (logout), which also generates a new anonymous_id.
- **Server events** carry the `anonymous_id` (and `user_id` if known) that the browser passes with the order request, linking the order to the visitor's journey.
- Unique visitors are counted by distinct `anonymous_id` in the range. Limitation: the same person on two devices counts twice unless identified; we do not retroactively merge identities in counts.

## 6. Event contract

```ts
type EventType = 'page_view' | 'track' | 'identify';

interface AnalyticsEvent {
  event_id: string;          // UUID v4 generated by SDK; idempotency key
  type: EventType;
  name: string;              // 'page_view' | 'identify' | custom (1–100 chars, [a-zA-Z0-9_.:-])
  anonymous_id: string;      // required for browser events; optional for server events if user_id present
  user_id?: string | null;
  session_id?: string | null;
  timestamp: string;         // ISO 8601, client time
  url?: string | null;       // path + query (page_view and track)
  title?: string | null;
  referrer?: string | null;
  properties?: Record<string, unknown>; // JSON, ≤ 8 KB serialized
}
```

Batch envelope: `{ "events": AnalyticsEvent[] }` with 1–50 events, body ≤ 64 KB.

Server-side normalisation:
- `received_at` = server time.
- `occurred_at` = client `timestamp`, unless it is more than 24 h in the future or more than 7 days in the past, in which case `received_at` is used (clock-skew guard).
- `source` = `browser` or `server` depending on endpoint.
- `user_agent` taken from request header (browser endpoint only). IP is **not stored** (privacy); only used in-memory for rate limiting.

## 7. Database schema (SQLite)

```sql
CREATE TABLE projects (
  id               TEXT PRIMARY KEY,
  name             TEXT NOT NULL,
  public_key       TEXT NOT NULL UNIQUE,
  secret_key_hash  TEXT NOT NULL,          -- sha256 of secret key
  allowed_origins  TEXT NOT NULL,          -- JSON array of origins
  created_at       TEXT NOT NULL
);

CREATE TABLE events (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  event_id      TEXT NOT NULL,
  project_id    TEXT NOT NULL REFERENCES projects(id),
  type          TEXT NOT NULL,
  name          TEXT NOT NULL,
  source        TEXT NOT NULL,             -- 'browser' | 'server'
  anonymous_id  TEXT,
  user_id       TEXT,
  session_id    TEXT,
  url           TEXT,
  title         TEXT,
  referrer      TEXT,
  user_agent    TEXT,
  properties    TEXT,                      -- JSON string
  occurred_at   TEXT NOT NULL,             -- ISO 8601 UTC
  received_at   TEXT NOT NULL,
  UNIQUE (project_id, event_id)
);
CREATE INDEX idx_events_project_time      ON events (project_id, occurred_at);
CREATE INDEX idx_events_project_name_time ON events (project_id, name, occurred_at);
```

- Inserts use `INSERT OR IGNORE` → retries/duplicates are idempotent.
- A batch is inserted in one transaction.
- `PRAGMA journal_mode = WAL` for concurrent reads during writes.
- Schema is applied on startup (`CREATE TABLE IF NOT EXISTS`); a demo project is upserted from env vars.
- Tests use `:memory:` databases.

## 8. API

### Ingestion

| Endpoint | Auth | Notes |
|---|---|---|
| `POST /api/collect` | `publicKey` in body or `X-Analytics-Key` header; `Origin` must be in project's `allowed_origins` | CORS enabled for allowed origins; accepts `text/plain` body too (for `sendBeacon`) |
| `POST /api/server-events` | `Authorization: Bearer <secret key>` | No CORS; server-to-server only |

Response: `202 { accepted: number, duplicates: number, rejected: [{ index, error }] }`.
Errors: `400` malformed envelope, `401` bad key, `403` disallowed origin, `413` body too large, `429` rate limited (with `Retry-After`).

Per-event validation: invalid events are rejected individually; valid events in the same batch are still stored.

Rate limit: in-memory fixed window, 120 requests/min per (key, IP). Limitation: per-process only.

### Stats (dashboard)

All take `from`, `to` (ISO dates, inclusive day range, UTC) and validate `to - from ≤ 366 days`.

| Endpoint | Returns |
|---|---|
| `GET /api/stats/overview` | `{ pageViews, uniqueVisitors, sessions, events, orders, revenue }` |
| `GET /api/stats/timeseries?interval=day` | `[{ date, pageViews, uniqueVisitors }]` with zero-filled days |
| `GET /api/stats/top-pages?limit=10` | `[{ url, views, uniqueVisitors }]` |
| `GET /api/stats/events` | `{ names: string[], series: [{ date, [name]: count }] }` for non-page_view events |

Auth: dashboard login with `DASHBOARD_PASSWORD` from env sets an HTTP-only signed cookie; stats routes and `/dashboard` require it. Limitation: single shared password, no user accounts.

## 9. Browser SDK (`@acme/browser-sdk`)

Public API:
```ts
init({ publicKey, endpoint, autoPageViews = true, flushInterval = 5000, maxBatchSize = 20, debug = false })
track(name, properties?)
page(properties?)             // manual page view
identify(userId, traits?)
reset()                       // logout
optOut() / optIn()
getAnonymousId()              // so the app can pass it to its server
flush(): Promise<void>
```

Behaviour:
- **Auto page views:** on init and on history changes (patched `pushState`/`replaceState` + `popstate`), deduped when URL unchanged.
- **Queue:** in-memory, mirrored to `localStorage` (`acme_queue`) so events survive reloads/offline. Cap 500 events; drop oldest when full.
- **Flush:** every `flushInterval` ms or when queue reaches `maxBatchSize`; one request in flight at a time; batches of ≤ 50.
- **Retry:** on network error / 5xx / 429 → exponential backoff (1s, 2s, 4s, 8s, 16s, capped 30s, with jitter), events stay queued. On 4xx (except 429) → drop the batch (it will never succeed) and log in debug mode.
- **Page hide:** on `visibilitychange` → hidden / `pagehide`, send the queue with `navigator.sendBeacon` (text/plain JSON). Events remain persisted until a normal flush confirms them; duplicates are handled by server-side `event_id` dedup.
- **Safety:** every public method is wrapped in try/catch; the SDK never throws into the host app. No-ops during SSR (no `window`).
- **Privacy:** respects `navigator.doNotTrack === '1'` and `optOut()` (persisted).
- **React helper:** not required; the demo calls `init` in a client component in the root layout.

## 10. Server SDK (`@acme/server-sdk`)

```ts
const analytics = new ServerAnalytics({ secretKey, endpoint, timeoutMs = 2000, maxRetries = 2 });
await analytics.track(name, properties, { anonymousId?, userId? }); // never throws
```
- Generates `event_id` and `timestamp`.
- Uses `fetch` with `AbortController` timeout; retries on network error/5xx with short backoff.
- Returns `{ ok: boolean, error?: string }`; logs failures; never throws, so business logic (placing an order) is never blocked by analytics outages.
- Limitation: no durable outbox — if all retries fail, the event is lost (documented; production would use an outbox table or queue).

## 11. Dashboard (`apps/analytics` → `/dashboard`)

- Login page (`/login`) → password → cookie.
- Date-range control: presets Today / Last 7 days / Last 30 days + custom from/to; state in URL query string.
- KPI cards: Page views, Unique visitors, Sessions, Orders (+ revenue).
- Line chart: page views & unique visitors per day.
- Table: top pages.
- Chart: custom event trends per day (add_to_cart, order_created, …).
- Loading, empty and error states.

## 12. Restaurant demo (`apps/restaurant`)

- Pages: `/` home, `/menu`, `/cart`, `/checkout`, `/order/[id]` confirmation, `/login`.
- Menu is a static list; cart in `localStorage`; orders stored in-memory/JSON file in the demo app (it is not the analytics DB).
- Tracked: auto page views; `menu_item_viewed`, `add_to_cart`, `remove_from_cart`, `checkout_started` (browser); `identify` on login; `order_created` (server, from `POST /api/orders` route using the server SDK with the anonymous_id sent by the client).
- A small banner links to the dashboard.

## 13. Testing

- **shared:** schema accepts valid events, rejects invalid names/oversized properties.
- **browser-sdk (jsdom):** id persistence; session rotation after 30 min; batching by size and interval; retry with backoff on failure and success after recovery; queue persisted and restored; 4xx drops batch; sendBeacon on pagehide; never throws; opt-out/DNT.
- **server-sdk:** sends bearer key; timeout; retries on 5xx; never throws.
- **analytics API:** 401 bad key, 403 bad origin, partial batch acceptance, duplicate event_id stored once, clock-skew normalisation, rate limit 429.
- **stats queries:** overview counts, unique visitors, sessions, zero-filled timeseries, top pages, date-range boundaries — over fixed fixtures in `:memory:`.
- **end-to-end (integration):** server SDK → real route handler → stats returns the order.

## 15. Assumptions

- Single tenant demo; one seeded project, multi-project-capable schema.
- UTC days for all reporting.
- "User activity" = custom events + identified users; "order created" = server-side business event.
- Reviewer runs locally on Node 20+.

## 16. Limitations and next steps

- SQLite single-writer; for scale move to Postgres (OLTP) or ClickHouse (analytics) and ingest via a queue.
- Aggregates computed at query time; at scale add daily rollup tables.
- In-memory rate limiting is per-process; use Redis in production.
- Server SDK has no durable outbox.
- Dashboard auth is a shared password.
- No bot filtering, geo, or device breakdowns.
- Identity merge is not applied retroactively to visitor counts.
